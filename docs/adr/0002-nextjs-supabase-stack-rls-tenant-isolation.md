# Next.js + Supabase stack, with RLS-enforced tenant isolation and no ORM

We're building a mobile-responsive, multi-tenant (strictly single-user-per-account, no sharing) SaaS journaling app as a learning project, prioritizing free/cheap hosting. Four stacks were researched against official docs/pricing (issue #3, `docs/research/stack-hosting-fit.md` on the `research/stack-hosting-fit` branch): Next.js/Vercel + Neon or Supabase Postgres; SvelteKit/Cloudflare Workers + D1; a Supabase-centric stack (Auth + Postgres + RLS + Edge Functions) with any frontend host; and Fly.io/Railway Dockerized. Fly.io/Railway were ruled out — neither has a durable free tier for an always-on app plus Postgres (Fly Managed Postgres starts at $38/mo; Railway's post-trial free allowance is $1/mo, with trial volumes deleted 30 days after credit expiry). Cloudflare Workers was ruled out — its 10ms CPU-time-per-invocation budget is a poor fit for a database-heavy CRUD app, and it has no built-in auth service.

We chose **Next.js (App Router) on Vercel (Hobby tier), backed by Supabase (Postgres + Auth + Row Level Security + Edge Functions)** — blending the two strongest researched options. Tenant isolation is enforced by **RLS policies keyed on `auth.uid()`**, not by manual `user_id` checks scattered through application code, using Supabase's official `@supabase/ssr` package for session handling across Next.js server components and route handlers. A Supabase **service-role key is reserved only for operations that must bypass RLS** (e.g. Stripe webhook handlers writing subscription state without an active user session). Schema and migrations are managed via the **Supabase CLI** (SQL migrations + generated TypeScript types) — deliberately **no separate ORM** (Prisma/Drizzle) layered on top, to avoid splitting "app-owned schema" from "DB-owned RLS policy" across two different tools.

Supabase Auth is wired directly to Postgres RLS, which is the natural mechanism for this app's per-tenant isolation requirement: the database itself enforces that one user can never see another's journal, rather than relying on every handler remembering to filter correctly. Vercel + Next.js gives zero-config git-push deploys and the largest ecosystem — valuable specifically because this is a learning project. Known, accepted tradeoff: Supabase's free-tier project auto-pauses after 1 week of inactivity (one-click resume from the dashboard, not a rebuild) — acceptable friction at personal scale, not a hard wall.
